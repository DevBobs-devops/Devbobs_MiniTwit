\subsection{Design and architecture of our ITU-MiniTwit
systems.}\label{design-and-architecture-of-our-itu-minitwit-systems.}
\textit{marho@itu.dk} \\

The architecture of MiniTwit follows, as Chirp, the onion architecture. 
The deployment architecture of the MiniTwit system can be seen in figure \ref{deployment-diagram}.
The architecture strives to achieve high-availability by having a swarm of five nodes.
A user can reach MiniTwit with the domain \texttt{Devbobs.tech} on port 433 or 80, which redirects to 443.
The request will reach the Leader node and will then get loadbalanced by Caddy between the four instances of MiniTwit running.
MiniTwit is also available on port 8080 with http. The request will in this case be loadbalanced by the docker ingress routing mesh.
The architecture have a single point of failure, which will be explained in section \ref{availability}.
The rest of the services, like Grafana, can be reached on their corresponding port using the floating ip or any of the nodes IP. \\

\subsection{Current state of system}\label{current-state-of-system}
\textit{marho@itu.dk} \\

To keep software quality high and later ease maintainability of the application we follow several practices and use a set of different tooling. 

\subsubsection{Practices}
The first practice is code reviews. No code gets pushed to main before it has been approved by atleast one other group member. This is done though GitHub pull-requests.
Combined with the use of GitHub issues, this gives a clear picture of why, what and how a feature have been implemented.
The use of conventional commits like: \texttt{feat:}, \texttt{chore:}, \texttt{note:}, have been used to give a clear view of what each commit in the git history do. 

\subsubsection{Tooling}
Tooling have been used to assist keeping quality high.
This is especially usefull as the project grew bigger. 
First, we use automatic testing, which have caught many problems. 
This is done in our continous intergration (CI) pipeline: Build and Test, which runs tests, a formater and a linter.
These can be seen in \ref{build-and-test}. \\

Next we have SonarQube which is used to analyse code quality and security issues as seen in \ref{sonarqube}.
The current state of the system, according to SonarQube, is acceptable - SonarQube scores Security: C, Reliability: A and Maintainability: A, as seen in Figure~\ref{sonarqube-report}.
The low score on security fails means we fail SonarQube's Quality Gate, which is an issue.
